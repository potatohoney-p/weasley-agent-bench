# Opt-in check-level regression gate

Task-level comparison intentionally reports a regression only when a previously
passing task fails. If a task already fails `final[0]`, newly losing `final[1]`
leaves it failing; the legacy task transition remains `unchanged`. This is the
existing binary-task contract, not an evaluator defect.

For callers who must protect already-working parts of incomplete tasks, select
`compare(..., check_regressions=True)` or
`compare_jsonl(..., check_regressions=True)`. Both CLI comparison commands accept
`--check-regressions`. The Python option must be a boolean; omission/False preserves
all legacy report fields and behavior.

## Synthetic reproduction

```sh
python -m weasley_agent_bench compare examples/check-regressions/suite.json examples/check-regressions/baseline.json examples/check-regressions/candidate.json
# exit 0: both runs fail the task, so there is no task-pass regression
python -m weasley_agent_bench compare examples/check-regressions/suite.json examples/check-regressions/baseline.json examples/check-regressions/candidate.json --check-regressions
# exit 1: final[0] improves, but final[1] newly fails; gains cannot cancel losses
```

These are hand-authored synthetic observations, not model performance results.
The JSONL command selects the same policy and produces an equivalent logical
report through its existing bounded input and scratch-storage transport.

## Identity, completeness and missing evidence

Both sides are rescored against the same validated supplied suite and paired by
task ID. Every suite task must have exactly one result on each side. Missing,
duplicate, unknown-task and wrong-suite-ID runs fail rather than dropping cases.
As before, rescoring does not prove which historical contract a runner actually
used; provenance remains a separate optional workflow.

Checks are generated by the existing evaluator, not supplied comparison reports.
Identity is the task ID plus its existing named check code: `result.present`,
`result.completed`, indexed final/tool expectations, `tools.count`,
`tools.forbidden`, and named budget checks where configured. The same task
contract generates the same check identities even when outcomes differ. The
comparison rejects duplicate/mismatched identities or non-boolean results rather
than guessing how to pair them. Output order follows the baseline evaluator's
stable check order; input result order has no effect.

Missing measured usage for a configured budget is a failed budget check, not
zero or an absent check. A tool sequence that fails to supply a required step
similarly yields a failed named step check. Cancelled/error task results remain
visible and have a failed completion check. An unchanged false check does not
become a new regression; only true→false transitions do. False→true transitions
are separate improvements and never subtract from losses.

## Opt-in report extension

The input schemas and default reports are unchanged. Selected reports retain
schema version 1 and explicitly identify this extension with
`regression_policy: "checks-v1"` (in the JSONL header).

- Each task change adds `check_regressions` and `check_improvements`, ordered
  lists of named codes. Existing task `change` and `failed_checks` remain intact.
- `summary.regressions` / `improvements` still count **task-pass transitions**.
  New `summary.check_regressions` / `check_improvements` count individual check
  transitions, and `tasks_with_check_regressions` counts affected tasks.
- `task_no_regressions` preserves the original binary-task gate.
- `no_regressions` now selects the requested check gate: true exactly when no
  named check newly fails. The CLI exits 0/1 from that selected gate; malformed
  input remains exit 2. `candidate_passed` keeps its original all-task meaning.

For example, `no_regressions: false` with `summary.regressions: 0` is intentional
when an already failing task loses another check. Consumers must inspect the
policy marker and the explicitly named check summary, not reinterpret the old
counter. A passing gate does not mean the candidate passes all tasks.

JSONL ingestion, scoring, identity matching and report spooling finish before
output. Completion follows successful scratch cleanup; a prefix without terminal
is incomplete, and consumers must check the process exit code as well. The new
per-task lists are bounded by checks in the current task record, not by total
suite size; output/scratch can grow. No new whole-process constant-memory or
performance claim is made.

Check counts are dependent and unweighted diagnostic counts, not independent
trials, a quality score, significance, or a comparable ranking across different
contracts. Repeated-run statistics, scoring rules, provider execution and artifact
provenance are unchanged.
